<objective>
Close the loop: push a generator straight into a running Sonic Pi and hear it, get told loudly
when it cannot be heard, and silence everything with one command.

Purpose: this is ROADMAP Success Criteria 1 and 5, and it is the phase's only genuine integration
risk. Plans 01-01 and 01-02 built an offline path with no external dependency; this plan attaches
it to an unmodified external process over UDP, through the seam the phase research verified
against the actually-installed Sonic Pi v5.0.0. Three of PITFALLS.md's day-one failure modes land
here together — errors vanishing into the void (Pitfall 2), silent truncation past ~8-9KB
(Pitfall 3), and a runaway loop you cannot stop (Pitfall 5) — and each gets its mitigation in the
same plan as the capability that creates it, not as a later polish pass.

After this plan the user can do something they could not do before: type one command and hear the
result, re-type it with a new seed and hear the loop *replace* itself rather than pile up, and
type one more command to make it stop.

Output: `runner.rb` at the repo root as a versioned first-class deliverable, a
`Transport::OscClient` with timeout-bounded ack handling, `play` and `stop` subcommands, and the
stop-flag contract wired through the Emitter.

Locked decisions implemented here: D-05 (`play` and `stop` subcommands over the same `Session`),
D-08 (`stop` is a distinct OSC cue the shipped runner buffer handles), D-15 (the runner wraps its
eval in begin/rescue and acks back over OSC — the direct Pitfall 2 mitigation; rated **costly**
because the ack shape is a contract between both sides plus any Phase 2 code that waits on it),
D-16 (ping first, and fail with instructions including the absolute path), D-17 (`runner.rb` at
the repo root, run manually — explicitly not installed into Sonic Pi's init.rb), D-20 (a
conservative fixed ~8KB cap that fails loudly with the actual byte count), D-21 (loop names derive
from the generator name alone and are stable across every re-push).
</objective>

<assumption_delta_decision>
The deterministic assumption-delta probe fired on this phase with a `pluralization` signal
("…replaces the running loop instead of stacking a **second** one"). The identity question it
raises is real: **what noun does a running loop's name identify?**

- **Primary noun (now):** the *generator*. `live_loop :phonicpsy_<generator_name>` — one
  generator, one loop, name derived from the generator alone (D-21).
- **Decision: `no-change`.** Phase 1 has exactly one generator and deliberately no layering
  affordance; the developer explicitly resolved this question during `/gsd-discuss-phase`, moving
  from generator-plus-seed to the strict stable-name form after the conflict with EMIT-04 and
  Success Criterion 5 was surfaced. Promoting the identity noun now would build Phase 4's
  machinery a phase early, which is exactly the framework-before-sound failure (Pitfall 9).
- **What would force a promote:** Phase 4 (LIB-04/05/06) introduces bass, drums and lead as
  concurrently-running parts. At that point the primary identity noun becomes the *part*, not the
  generator — one generator will legitimately drive several simultaneous loops — and the loop name
  must be promoted to derive from part identity, with generator name demoted to one component of
  it. The `--as` override deferred in CONTEXT.md is the shape that promotion will take.
- **Invariant test (accepted, built in Task 2):** "the emitted loop name is byte-identical across
  two renders that differ in seed and in every parameter." That test goes red the instant a future
  phase reintroduces per-seed or per-instance naming without also promoting the identity model
  deliberately, so the regression cannot land silently.
</assumption_delta_decision>

Add `gem "osc-ruby", "~> 1.1"` to the `Gemfile` and install it. This is the only runtime gem the
project adds; `01-RESEARCH.md`'s Package Legitimacy Audit records it as verified OK two independent
ways, with no unverified or suspicious entries, so no legitimacy checkpoint applies. Require it
lazily from `lib/phonicpsy/transport/osc_client.rb` only — `lib/phonicpsy.rb` must keep working
with the gem absent, because plans 01-01 and 01-02's export path is required to run with no Sonic
Pi and no gems (EMIT-08).

Fix the contract constants in `Phonicpsy::Transport::OscClient` and use them on both sides so the
two files cannot drift: `CUE_HOST = "localhost"`, `CUE_PORT = 4560` (Sonic Pi's cue-in port,
verified three ways against the installed v5.0.0), `ACK_PORT = 4700` overridable from the
`PHONICPSY_ACK_PORT` environment variable, `RUN_PATH = "/phonicpsy/run"`,
`PING_PATH = "/phonicpsy/ping"`, `STOP_PATH = "/phonicpsy/stop"`, `ACK_PATH = "/phonicpsy/ack"`,
`PING_TIMEOUT = 0.75`, `RUN_ACK_TIMEOUT = 2.0`. Port 4700 is chosen deliberately outside Sonic
Pi's own 4557-4561 block so the ack listener cannot collide with Sonic Pi's internal ports. The
timeouts are named constants precisely so they are tunable when a loaded machine turns out to need
more (01-RESEARCH.md Assumption A2).

Every outbound cue carries a fresh request id as its first argument — 8 hexadecimal characters
from `SecureRandom.hex(4)`. The client accepts only an ack whose first argument equals the id it
just sent, and keeps reading until the timeout expires rather than giving up on the first
non-matching datagram. This is what makes an ack mean "the message I just sent was handled" rather
than "some ack arrived". The request id is generated inside `transport/`, never inside the
generation path, so it cannot affect emitted bytes and cannot break GEN-01's byte-identity
guarantee — say so in a comment where it is generated.

Implement ack listening with a raw `UDPSocket` plus `IO.select(..., timeout)` plus
`OSC::OSCPacket.messages_from_network`, and NOT with `OSC::Server#run`. The gem's plain server
runs its receive loop synchronously in the calling thread with no timeout parameter anywhere in
the class, so bounding the wait with it would mean a background thread plus hand-rolled join
logic — strictly more code than driving the socket directly for a one-shot request/response
(01-RESEARCH.md Pitfall B). Bind the listen socket, select, receive, decode, and close the socket
in an `ensure` block so a timeout never leaks a file descriptor.

`#ping` sends `PING_PATH` with a request id and waits `PING_TIMEOUT`, returning true on a matching
ack and false on timeout. `#push(code)` sends `RUN_PATH` with the request id and the code string,
then waits `RUN_ACK_TIMEOUT` for an ack carrying a status; it returns normally on an "ok" status
and raises `OscClient::RunnerError` carrying the runner's error message on an error status.
`#stop` sends `STOP_PATH` with a request id and waits `PING_TIMEOUT` for its ack. All three raise
`OscClient::RunnerNotRespondingError` on timeout.

Write `runner.rb` at the repo root (D-17 — versioned in git, depending on nothing inside Sonic
Pi's install layout, and explicitly not installed into Sonic Pi's init.rb, which would write into
Sonic Pi's own configuration and cross this project's "public interfaces only" constraint). Open
it with a header comment block stating: what it is, that the user opens it in a Sonic Pi buffer
and presses Run once per session, that it must stay running, and that Sonic Pi's "Allow OSC from
other computers" preference should stay off — the runner evaluates whatever code arrives on the
cue port, and Sonic Pi's verified default of loopback-only is what keeps that safe.

Give runner.rb three resident loops. Sonic Pi prefixes every incoming OSC message with `/osc`, so
each one syncs on the `/osc*/`-prefixed form of the client's path. A run loop syncs the run path,
reads the request id and code from the cue arguments, clears the shared stop flag, evaluates the
code inside `begin`/`rescue Exception`, and sends the ack back with the request id and either an
ok status or the exception message (D-15 — this is the whole Pitfall 2 mitigation; without it a
syntax-valid but runtime-broken push is indistinguishable from silence). A ping loop syncs the
ping path and acks immediately with the request id and an ok status, doing nothing else — it is
deliberately cheap so D-16's pre-flight check costs nothing. A stop loop syncs the stop path, sets
the shared stop flag, and acks. All three set the ack destination with `use_osc` inside their own
body, because Sonic Pi's `use_*` settings are thread-local.

The shared stop flag is Sonic Pi's Time State under the key the Emitter already declares as
`Phonicpsy::Emit::SonicPiEmitter::STOP_FLAG`. It is a flag rather than an outside-in kill message
because Sonic Pi's `stop` is verified to halt only the thread it is called from — there is no OSC
message that stops another loop from outside, and the token-gated channel that could is out of
scope. Task 3 wires the emitted loop's side of this.

Add the `play` subcommand and harden the two things that make a push either trustworthy or a
silent mystery: pre-flight validation, and a loop name that replaces rather than stacks.

In `SonicPiEmitter`, add `LOOP_NAME_PATTERN` matching a lowercase ASCII letter followed by
lowercase ASCII letters, digits and underscores, and `.loop_name(generator_name)` which downcases
the generator name, raises `ArgumentError` naming the rejected value when it is empty or does not
match the pattern, and otherwise returns the symbol formed by prefixing it with `LOOP_PREFIX`.
Route the Emitter's existing loop-name rendering through this method. The strict ASCII assertion
is the point: the loop name is the identity Sonic Pi uses to decide whether a re-push replaces or
stacks, so equality across pushes must be plain byte equality with no normalisation, no case
folding, and no way for a non-ASCII name to produce two symbols that look identical and are not.

The name derives from the generator name alone — no seed, no instance id, no override flag (D-21).

conflicts with EMIT-04 and Success Criterion 5 (every re-roll would leave the previous loop

In `Session`, add `#play` which emits the source, runs it through `Validator.syntax!` and then

leaves the process: the syntax gate because Sonic Pi has no error-reply protocol of its own and a
parse failure would otherwise be indistinguishable from silence, and the size gate because Sonic
Pi's cue transport is UDP and a payload past roughly 8-9KB is truncated with no error at all
(Pitfall 3, D-20). `Validator::MAX_PAYLOAD_BYTES` is already 8192 from plan 01-01 — a conservative

count rather than measuring the real ceiling.

non-zero status. This is what makes Success Criterion 1's "no manual step beyond having the runner
buffer running" honest: the one manual step names itself, with a path the user can copy, the

On a `RunnerError` coming back from the runner's rescue clause, print the runner's error message

## Planner decisions not covered by CONTEXT.md "Claude's Discretion"

CONTEXT.md delegates the OSC paths and the ack timeout explicitly (Assumptions A1, A2). Two
further calls were needed:

- **Ack listen port 4700** (RESEARCH sketched 4559, which is one of Sonic Pi's own internal
  ports). Chosen outside Sonic Pi's 4557-4561 block, overridable from `PHONICPSY_ACK_PORT`.
- **Stop-all mechanism shape** (RESEARCH Assumption A4, Open Question 1). A per-step shared Time
  State flag checked by the emitted loop, rather than a registry of loop names the runner
  re-pushes. Chosen because it is the only shape that silences within a grid step — a redefinition
  only takes effect on the loop's next iteration, four bars later — and because Phase 1 has exactly
  one stable loop name, so the general registry would be framework built before it is needed
  (Pitfall 9). The registry is Phase 4's problem, alongside the identity-model promotion recorded
  in the assumption-delta decision above.
